# IntellaFeeder — from v2.5 to v3.1b

*(Version française plus bas — [aller au français](#intellafeeder--de-la-v25-à-la-v31b))*

Baseline for this document: **v2.5l**, the last executable of the v2.5 series
(full FR/EN localisation and five hardening batches). Everything below landed
between 6 and 11 September 2026.

Two sentences to sum it up: **v2.6 → v2.9d taught the tool things it did not
know** (compound cases, drag-and-drop, MIME type names, what a profile can and
cannot replay); **v3.0 → v3.1b reorganised the window around the actual job**
and stopped it getting several things wrong on screen.

Nothing changed in what the tool *writes*. The JSON descriptors, the task files
and the resilient `.bat` are, byte for byte, what v2.5 produced.

---

## At a glance

| | What it brought |
|---|---|
| **v2.6 → v2.6b** | Compound cases: detected, read sub-case by sub-case, Import closed |
| **v2.7 → v2.7d** | Feeding the Import: drag-and-drop from Explorer, recursive image scan |
| **v2.8** | One button for the whole import; UNC-host-insensitive de-duplication |

## Compound cases (v2.6)

A compound case holds **no source of its own**: it references sub-cases, carries
the total size of the set, and lists the users authorised on it.
`-addSourcesFromJson` cannot add a source to one.

- Detection is on `compound="true"` plus a `<subcases>` block.
- The inventory runs **one `-exportSourceList` per sub-case**, never one on the
  compound: it is the only way to attribute each source to its sub-case (a
  "Sub-case" column appears in the table and the CSV).
- A sub-case that cannot be reached does not abort the others. Each one carries
  its own verdict, and the word "PARTIAL" appears as soon as one is missing — an
  incomplete inventory is never presented as complete.
- The Import tab is **greyed out** on a compound, with a second guard inside the
  functions themselves.
- The folder-size cache is written **per sub-case**, never at the compound
  level: the composition of a batch changes, and a single cache would outlive
  cases that are no longer part of it.

⚠ **The UNC host trap.** A compound can declare its sub-cases by IP while the
compound itself is opened by host name. Windows opens **one SMB session per
server name**: the session by IP was readable (the sub-cases showed up) but
refused writes, and `-exportSourceList` failed on the `case.xml.lock` — *with a
return code of 0*. IntellaFeeder now rewrites the sub-case's host to the one the
compound is already open through, when the share is the same and the folder
exists, and falls back to the declared path otherwise.

## Feeding the Import (v2.7)

Drag-and-drop from Explorer, and recursive collection of forensic images. This
replaced an external tool that used to build the path lists.

**The two panes do not treat a dropped folder the same way, and it is written
under each of them:**

- **Forensic images**: a dropped folder is explored and only known images are
  added, **first segment only** (a 40-segment image becomes one line). Everything
  else is left out **with its reason**, never silently.
- **Standard folders**: what you drop becomes the source, with no inspection.

Extensions kept: `E01 Ex01 L01 Lx01 S01 DD AD1 VMDK VHD VHDX` plus `.001`; VMDK
annexes (`-s001`, `-flat`, `-delta`, `-ctk`) are left out. This list is not
widened "just in case": a source added by mistake goes to the import, and
Intella does not let you review a source's settings afterwards.

Drag-and-drop is implemented in **ctypes**, not `tkinterdnd2` — the "no external
dependency, self-contained exe" contract wins. An `enable_dnd = 0` switch in the
`.ini` turns it off without rebuilding, for a machine that would not get along
with it.

Sub-folder exploration is **off by default** at install (a seals folder often
sits next to other cases or working copies; descending by default would bring in
foreign images, and the mistake would only show after indexing). Since v2.9 its
*starting* state is a preference. And an empty pass is distinguished from a
breakdown: when nothing is found and the folder has sub-folders, the tool says
so and **offers to descend**.

---

## One button for the whole import (v2.8)

"▶ Run the full import" chains Generate → Import → Validate with no intermediate
confirmation. The three steps remain reachable under "Steps ▾", because a `.bat`
launched outside the application still has to be validated by hand.

🐞 And a real defect fixed there: **de-duplication now compares paths
host-blind**. Measured on a real export — one source recorded by IP and three by
NetBIOS name, same share. Comparing raw paths let an already-indexed source go
back to the import. Every match obtained that way is logged, because the
trade-off (two different servers, same share name and sub-path) is a knowingly
accepted false positive.

## The MIME type reference (v2.9, reversed in v3.1)

Intella identifies what it indexes by MIME type name, and a source's type filter
is a plain list of those names. Two things make that list hard to read.

**A filter is read backwards if its mode is left unsaid.** In Intella's GUI you
tick what you *want*; the export records the *complement*. So
`Exclude selected entries` followed by six hundred types means those six hundred
are the ones left out — the less you tick, the longer the list. The tool always
states what the list actually *does*, and since v3.1a that sentence carries the
colour: red for "these types are excluded", green for "only these types are
indexed".

**Intella writes synonyms it never describes.** Measured on a near-exhaustive
real filter (677 distinct names): **121 are absent from the reference list**,
18 %. For Word alone: `application/msword`, `application/winword`,
`application/word`, `application/doc`, `zz-application/zz-winassoc-doc`, when the
reference only describes `application/vnd.ms-word`. Treating "absent" as an error
would put 121 red alerts on a single source, and teach you to stop looking at the
colour. Hence **four states, never two**: described by Vound, described by you,
known but unlabelled, and genuinely unknown.

679 descriptions and 800 type names are **built into the executable**, and the
tool learns new names from every case it reads — automatically, at each
successful inventory read. There is nothing to run for that.

🔄 **The import contract was reversed in v3.1.** A `.properties` file dropped in
used to *replace* the built-in descriptions, so that a type Vound had withdrawn
would stop being described. In practice that is not what you want — "I don't know
whether it replaced or accumulated" — and **you import to gain labels, not to
lose them**. Imports now accumulate into a single cumulative file, the newest
wins collisions, and nothing already known is lost. A "Comes from" column says
where each label comes from.

## What a profile can and cannot replay (v2.9a)

A question worth settling was: can a profile pick up **all** the settings of a
source configured by hand in Intella, including the ones IntellaFeeder does not
know about? Five rounds of trials on a throwaway case (11 imports) answered: **no,
and it cannot be made to.**

`-addSourcesFromJson` works on a **white list of names**. Anything not on it is
dropped **in silence** — no error, no warning, no effect. Checked on the
*re-exported* XML, never on the log: a real, undocumented XML key
(`isReindexingAllowed`) comes back at its default, and so does an option
documented under a different name (`indexMailContainers`). Export and import are
not two faces of one model: the XML serialises the *internal state*, the JSON
parses a *public API* whose every key is wired by hand.

So rather than pretend, the tool **shows**. The "Source settings" viewer lists
every setting of an exported source in three colours: replayed by the profile,
known but to be redone by hand in Intella, and unknown — which almost always
means your Intella is newer than the tool's catalogue.

⚠ Three vocabularies, not two: internal XML (`analyzeParagraphs`,
`crawlerMaxBinarySize`), CLI (`-indexVolumesShadowCopies`) and JSON
(`analyseParagraphs`, `indexVolumeShadowCopies`). Never copy a name from one
dialect to another without testing it — and note that a **recognised** key,
badly filled in, makes the import *fail*, where an unknown key is merely ignored.

## Colour is a signal, not decoration (v2.9c)

Six tabs, seven button colours: when everything is coloured, nothing stands out
and the eye cannot find the action of the screen. Four roles, and nothing else:

| Colour | Role |
|---|---|
| **Green** | the action that advances the work — **one per panel** |
| **Red** | destructive, or an anomaly to deal with |
| **Orange** | attention: something is still to be done |
| **Blue / purple** | a jump to another screen |

Everything else is neutral. v3 adds a fifth tint that is *not* a button role: a
teal used for chrome (current step, focus, selection, table headers), and a
second button **level** — coloured buttons are filled, neutral ones are outlined.
Before that, ten filled buttons all carried the same weight and the panel's
action drowned among them.

## v3.0 — the interface rework

### A trail, not a row of tabs

Fourteen screens were mocked up in HTML, in three directions and four screen
sizes, from 13″ to 27″. The direction chosen was **"Parcours"** (trail): the
window now shows **the job** — ① the case, ② import the sources — and keeps
aside, as **tools**, the four screens that are not part of it (case detail,
profiles, maintenance, help).

Each step carries a **state** — to do / in progress / done — computed from real
progress. Without that, the trail would only be a tab bar in disguise.

Under the hood the `ttk.Notebook` is kept, simply stripped of its tabs, so page
switching, sub-tabs and the greying-out of a compound case all keep working.

### Twelve decisions, taken on the mock-up

| Decision | Kept |
|---|---|
| Visual direction | **Trail** |
| Context bar replacing "common settings" | yes |
| Import parameters folded away | yes |
| "⋯" menu for rare actions | yes |
| Tick a whole task column from its header | yes |
| Task columns named (OCR/MD5 instead of T1/T2) | **no** — T1/T2 stay, real name in the tooltip |
| Already-indexed sources struck through rather than removed | yes |
| Profiles form in two columns | yes |
| Density and text-size setting | yes |
| Permanent status bar at the bottom | yes |
| Internal jargon removed from labels | yes |
| Log filters (All / Warnings / Errors) | yes |

### Density and text scale

Maintenance → Options: compact / normal / comfortable, plus a font scale from
80 % to 140 %, applied **without restarting** and remembered in the `.ini`. The
same window is meant to be usable on a 13″ laptop and on a large desk screen.

## v3.1 — ergonomics, after a day of use

- **Two steps, not three.** "Sources" and "Import" opened the same page.
- **Profiles: two sub-tabs, not three.** Four places used to talk about MIME
  types without talking to each other — a filter field, a two-pane popup, a
  category picker with checkboxes, and a reference sub-tab. Adding a type in the
  popup ticked nothing in the picker. They are now one screen, and the checkboxes
  are gone: a filter is composed by **adding entries** taken from the reference
  list, which also removes the need to ever compute a complement.
- **Secondary windows can be minimised** (no `transient()` — on Windows it turns
  a window into a tool window, which loses its Minimize button).
- **Help**: searchable with a hit counter, a capped reading width, and three
  **drawn** diagrams (the trail, include/exclude, a multi-segment image). Drawn,
  not screenshotted: a screenshot becomes wrong at the first UI touch-up.
- **Tooltips** wherever a label is right but mute — the three settings states,
  the four MIME states, what a filter mode does.

## v3.1a — the pass on screenshots

Six defects that only a screenshot shows: a pane footer stacked *after* its
table (buttons pushed into the opposite corner, counter cut to "33 t"); a button
wrongly greyed out; types with no label showing **their own name** as their
description, so the "no description" filter filtered nothing; help lines still

`disabled` staying bright green.

Plus: a type is now named **in one place only** (Maintenance → MIME types),
double-click adds on the right and removes on the left, and the filter mode's
**sentence** carries the colour instead of its label.

## v3.1b — translations

The MIME "comes from" column kept its three labels in a class constant, frozen
in French when the module was imported — before a language was even chosen. The
startup log had its first three lines hard-coded in French. And the `lang/`
folder was shown as "missing" in orange, like a fault to repair, when the
languages are *built into* the executable and that folder only exists to
*override* a translation without rebuilding; a new button seeds it.

**Known gap**: 11 log lines in `case_export.py` and `generator.py` are still
French. Those modules take a `log` callable and do not import the i18n layer by
design.

## Defects fixed along the way

The ones worth knowing, because each cost a session:

- **Crash on the first real drop** (v2.7): `widget.after()` was called from the
  window procedure. `mainloop()` releases the GIL; re-entering Tcl from a stack
  Windows owns kills Python with no trace. The procedure now only reads the
  HDROP and fills a queue.
- **Crash on the second language change** (v2.7c): a onefile exe relaunching
  itself inherits `_PYI_APPLICATION_HOME_DIR`, so the new process reused its
  parent's extraction folder. First restart passed, second failed on "Python
  interpreter not found". The environment is now purged before relaunching.
- **"Info Profil" read the displayed row, not the source** (v2.7): after the
  first sort, the Profiles tab would have filled with another source's settings,
  saying nothing.
- **A saved profile silently lost its type filter** (v3.1): moving the "Filters"
  group out of the form removed its key from the form's variables.
- **The log filtered by entry, not by physical line** (v3.1): IntellaCmd's output
  arrives as one call holding dozens of newlines, so a search kept the whole
  block — fifty lines for one match. It looked like "search only works on
  warnings"; warnings happen to be single-line.
- **"View the source settings…" opened empty** (v3.1a): a colour constant had
  gone away with deleted code and two lines still called it — `NameError` right
  after the header, a 940×600 window with two lines in it, and no error anywhere.
- **The cumulative MIME file was ordered by date** (v3.1a): two files written
  within the same second share a timestamp, and the sort then fell back on their
  names — a just-recorded import could be overwritten by an older file.

### How they were found, and what now catches them

Almost none of these are visible to the test suite: it covers **no widget**, on
purpose. Two scripts were added:

```powershell
python tests\manuel_construction.py    # builds the window WITHOUT showing it
python tests\manuel_fumee_v3.py <screen>
```

`manuel_construction.py` never steals focus, so it is usable while someone is
working on the machine; it is what caught the unbound profile filter. And
`tests/test_noms_definis.py` is an AST pass that fails as soon as a module cites
a name nothing defines — `py_compile` only ever looks at syntax.

---

## Upgrading from v2.5

Nothing to migrate. Profiles (`profils/*.json`), the settings file
(`intellafeeder.ini`) and the per-case cache (`IF_<case>.info`) are read as they
are. New `.ini` keys appear on first launch (`density`, `font_scale`,
`recursive_default`, `default_profile`, `enable_dnd`).

⚠ If you keep a `lang/` folder next to the executable, its files still take
**priority** over the built-in languages — and v2.5 files will lack every string
added since. Delete them (the built-in FR/EN are complete), or reseed the folder
from Maintenance → Files.

## Les cas compound (v2.6)

Un cas compound ne contient **aucune source en propre** : il référence des
sous-cas, porte la taille totale de l'ensemble et la liste des utilisateurs
autorisés. `-addSourcesFromJson` ne peut pas y ajouter de source.

- La détection se fait sur `compound="true"` et un bloc `<subcases>`.
- L'inventaire lance **un `-exportSourceList` par sous-cas**, jamais un sur le
  compound : c'est le seul moyen d'attribuer chaque source à son sous-cas (une
  colonne « Sous-cas » apparaît dans le tableau et le CSV).
- Un sous-cas injoignable n'interrompt pas les autres. Chacun porte son verdict,
  et le mot « PARTIEL » apparaît dès qu'il en manque un — un inventaire
  incomplet n'est jamais présenté comme complet.
- L'onglet Import est **grisé** sur un compound, avec une seconde garde à
  l'intérieur des fonctions elles-mêmes.
- Le cache des tailles de dossiers s'écrit **par sous-cas**, jamais au niveau du
  compound : la composition d'un lot bouge, et un cache unique survivrait à des
  cas qui n'en font plus partie.

⚠ **Le piège de l'hôte UNC.** Un compound peut déclarer ses sous-cas par IP
alors qu'il est lui-même ouvert par son nom d'hôte. Windows ouvre **une session
SMB par nom de serveur** : la session par IP était lisible (les sous-cas
s'affichaient) mais refusée en écriture, et `-exportSourceList` échouait sur le
verrou `case.xml.lock` — *avec un code retour 0*. IntellaFeeder réécrit
désormais l'hôte du sous-cas sur celui par lequel le compound est déjà ouvert,
si le partage est le même et si le dossier existe, et retente le chemin déclaré
sinon.

## Alimenter l'Import (v2.7)

Glisser-déposer depuis l'Explorateur, et collecte récursive des images
forensiques. Cela remplace un outil externe qui servait à constituer les listes
de chemins.

**Les deux panneaux ne traitent pas un dossier lâché de la même façon, et c'est
écrit sous chacun d'eux :**

- **Images forensiques** : un dossier lâché est exploré et seules les images
  connues y sont ajoutées, **premier tronçon uniquement** (une image de 40
  segments devient une ligne). Tout le reste est écarté **avec sa raison**,
  jamais en silence.
- **Dossiers standard** : ce qu'on lâche devient la source, sans inspection.

Extensions retenues : `E01 Ex01 L01 Lx01 S01 DD AD1 VMDK VHD VHDX` et `.001` ;
les annexes VMDK (`-s001`, `-flat`, `-delta`, `-ctk`) sont écartées. Cette liste
n'est jamais élargie « au cas où » : une source ajoutée par erreur part à
l'import, et Intella ne permet pas de revoir les réglages d'une source après
coup.

Le glisser-déposer est écrit en **ctypes**, pas avec `tkinterdnd2` — le contrat
« aucune dépendance externe, exe autonome » prime. Un interrupteur
`enable_dnd = 0` au `.ini` le coupe sans recompiler, pour un poste qui s'en
accommoderait mal.

L'exploration des sous-dossiers est **non récursive à l'installation** (un
dossier de scellés voisine souvent avec d'autres cas ou des copies de travail ;
descendre d'office ramènerait des images étrangères, et l'erreur ne se verrait
qu'après l'indexation). Depuis la v2.9, son *état de départ* est un réglage. Et
un passage à vide se distingue d'une panne : quand rien n'est trouvé et que le
dossier a des sous-dossiers, l'outil le dit et **propose de descendre**.

## Un seul bouton pour tout l'import (v2.8)

« ▶ Lancer l'import complet » enchaîne Générer → Importer → Valider sans
confirmation intermédiaire. Les trois étapes restent accessibles sous
« Étapes ▾ », car un `.bat` lancé hors application doit encore être validé à la
main.

🐞 Et un vrai défaut corrigé au passage : **le dédoublonnage compare désormais
les chemins à hôte près**. Constaté sur un export réel — 1 source enregistrée
par IP et 3 par nom NetBIOS, même partage. Comparer les chemins bruts laissait
repartir à l'import une source déjà indexée. Chaque correspondance obtenue par
cette voie est journalisée, car la contrepartie (deux serveurs différents, même
nom de partage et même sous-chemin) est un faux positif assumé.

## Le référentiel de types MIME (v2.9, renversé en v3.1)

Intella désigne ce qu'il indexe par des noms de types MIME, et le filtre de
types d'une source n'est qu'une liste de ces noms. Deux choses rendent cette
liste difficile à lire.

**Un filtre se lit à l'envers si l'on tait son mode.** Dans l'interface
d'Intella on coche ce qu'on **veut**, et l'export enregistre le **complément**.
`Exclude selected entries` suivi de six cents types signifie donc que ces six
cents-là sont écartés — moins on coche, plus la liste est longue. L'outil dit
toujours ce que la liste **fait** réellement, et depuis la v3.1a c'est cette
phrase qui porte la couleur : rouge pour « ces types sont exclus », vert pour
« seuls ces types sont indexés ».

**Intella écrit des synonymes qu'il ne décrit nulle part.** Mesuré sur un filtre
réel quasi exhaustif (677 noms distincts) : **121 sont absents du référentiel**,
soit 18 %. Pour le seul Word : `application/msword`, `application/winword`,
`application/word`, `application/doc`, `zz-application/zz-winassoc-doc`, quand le
référentiel ne décrit que `application/vnd.ms-word`. Traiter « absent » comme une
erreur ferait 121 alertes rouges sur une seule source, et apprendrait à ne plus
regarder la couleur. D'où **quatre états, jamais deux** : décrit par Vound,
décrit par vous, connu sans libellé, et réellement inconnu.

679 descriptions et 800 noms de types sont **embarqués dans l'exécutable**, et
l'outil apprend de nouveaux noms à chaque cas qu'il lit — automatiquement, à
chaque lecture réussie de l'inventaire. Il n'y a rien à lancer pour cela.

🔄 **Le contrat d'import a été renversé en v3.1.** Un `.properties` déposé
*remplaçait* les descriptions embarquées, pour qu'un type retiré par Vound cesse
d'être décrit. À l'usage ce n'est pas ce qu'on veut — « je ne sais pas si ça a
remplacé ou si ça s'accumule » — et **on importe pour gagner des libellés, pas
pour en perdre**. Les imports s'accumulent désormais dans un fichier cumulatif
unique, le plus récent gagne les collisions, et rien de ce qui était connu n'est
perdu. Une colonne « Vient de » dit d'où vient chaque libellé.

## Ce qu'un profil peut et ne peut pas rejouer (v2.9a)

Une question méritait d'être tranchée : un profil peut-il reprendre **tous** les
réglages d'une source réglée à la main dans Intella, y compris ceux
qu'IntellaFeeder ne connaît pas ? Cinq manches d'essais sur un cas jetable
(11 imports) ont répondu : **non, et on ne peut pas l'y forcer.**

`-addSourcesFromJson` travaille sur une **liste blanche de noms**. Ce qui n'y
figure pas est jeté **en silence** — pas d'erreur, pas d'avertissement, pas
d'effet. Contrôlé sur le XML *réexporté*, jamais sur le journal : une vraie clé
XML non documentée (`isReindexingAllowed`) revient à son défaut, et une option
documentée sous un autre nom (`indexMailContainers`) aussi. Export et import ne
sont pas deux faces d'un même modèle : le XML sérialise l'**état interne**, le
JSON parse une **API publique** dont chaque clé est câblée à la main.

Plutôt que de laisser croire le contraire, l'outil **montre**. Le visualiseur
« Réglages de la source » liste tous les réglages d'une source exportée en trois
couleurs : rejoué par le profil, connu mais à refaire à la main dans Intella, et
inconnu — ce qui signale presque toujours un Intella plus récent que le
catalogue de l'outil.

⚠ Trois vocabulaires, pas deux : XML interne (`analyzeParagraphs`,
`crawlerMaxBinarySize`), CLI (`-indexVolumesShadowCopies`) et JSON
(`analyseParagraphs`, `indexVolumeShadowCopies`). Ne jamais recopier un nom d'un
dialecte à l'autre sans l'éprouver — et noter qu'une clé **reconnue** mal
renseignée fait **échouer** l'import, là où une clé inconnue est seulement
ignorée.

## La couleur est un signal, pas une décoration (v2.9c)

Six onglets, sept couleurs de boutons : quand tout est coloré, plus rien ne
ressort et l'œil ne sait pas où est l'action de l'écran. Quatre rôles, et rien
d'autre :

| Couleur | Rôle |
|---|---|
| **Vert** | l'action qui fait avancer le travail — **une seule par panneau** |
| **Rouge** | destructif, ou anomalie à traiter |
| **Orange** | attention : il reste quelque chose à faire |
| **Bleu / violet** | renvoi vers un autre écran |

Tout le reste est neutre. La v3 ajoute une cinquième teinte qui n'est *pas* un
rôle de bouton : un teal réservé au chrome (étape courante, focus, sélection,
en-têtes de tableau), et un second **niveau** de bouton — coloré = plein,
neutre = en contour. Avant cela, dix boutons pleins se valaient tous et l'action
du panneau s'y noyait.

## v3.0 — la refonte de l'interface

### Un parcours, pas une rangée d'onglets

Quatorze écrans ont été maquettés en HTML, en trois directions et quatre tailles
d'écran, du 13″ au 27″. La direction retenue est **« Parcours »** : la fenêtre
montre désormais **le travail** — ① le cas, ② importer les sources — et range à
côté, en **outils**, les quatre écrans qui n'en font pas partie (détail du cas,
profils, maintenance, aide).

Chaque étape porte un **état** — à faire / en cours / fait — calculé sur
l'avancement réel. Sans lui, le fil ne serait qu'une barre d'onglets déguisée.

Sous le capot, le `ttk.Notebook` est conservé, simplement privé de ses onglets :
le changement de page, les sous-onglets et le grisage d'un cas compound
continuent de fonctionner tels quels.

### Douze décisions, arbitrées sur maquette

| Décision | Retenu |
|---|---|
| Direction visuelle | **Parcours** |
| Barre de contexte à la place des « paramètres communs » | oui |
| Paramètres de l'import repliés | oui |
| Menu « ⋯ » pour les actions rares | oui |
| Cocher une colonne de tâche entière par son en-tête | oui |
| Colonnes de tâches nommées (OCR/MD5 au lieu de T1/T2) | **non** — T1/T2 restent, nom réel en infobulle |
| Sources déjà indexées barrées plutôt que retirées | oui |
| Formulaire Profils sur deux colonnes | oui |
| Réglage de densité et de taille du texte | oui |
| Barre d'état permanente en bas | oui |
| Jargon interne retiré des libellés | oui |
| Filtres du journal (Tout / Alertes / Erreurs) | oui |

### Densité et échelle de texte

Maintenance → Options : compacte / normale / confortable, plus une échelle de
police de 80 % à 140 %, appliquées **sans redémarrer** et mémorisées au `.ini`.
La même fenêtre doit servir sur un portable 13″ comme sur un grand écran de
bureau.

## v3.1 — l'ergonomie, après une journée d'usage

- **Deux étapes, plus trois.** « Sources » et « Import » ouvraient la même page.
- **Profils : deux sous-onglets, plus trois.** Quatre endroits parlaient des
  types MIME sans se parler — un champ « filtre », un popup à deux panneaux, un
  sélecteur de catégories à cases à cocher, et un sous-onglet « référentiel ».
  Ajouter un type dans le popup ne cochait rien dans le sélecteur. Tout est
  réuni, et les cases à cocher disparaissent : on compose un filtre en
  **ajoutant** des entrées prises dans le référentiel — ce qui supprime du même
  coup le besoin de calculer un complément.
- **Les fenêtres secondaires sont réductibles** (plus de `transient()` : sous
  Windows, il transforme une fenêtre en fenêtre outil, qui perd son bouton
  Réduire).
- **Aide** : cherchable avec compteur de résultats, largeur de lecture
  plafonnée, et trois schémas **dessinés** (le parcours, include/exclude, une
  image multi-tronçons). Dessinés, pas photographiés : une capture d'écran
  devient fausse à la première retouche d'interface.
- **Infobulles** partout où un libellé est juste mais muet — les trois états des
  réglages, les quatre états MIME, ce que fait un mode de filtre.

Six défauts que seule une capture montre : le pied d'un panneau empilé *après*

Et aussi : on nomme désormais un type **à un seul endroit** (Maintenance → Types
MIME), le double-clic ajoute à droite et retire à gauche, et c'est la **phrase**
du mode de filtre qui porte la couleur, plus son intitulé.

## v3.1b — traductions

La colonne « Vient de » du référentiel MIME gardait ses trois libellés dans une

## Les défauts corrigés en chemin

Ceux qui méritent d'être connus, parce que chacun a coûté une session :

- **Crash au premier dépôt réel** (v2.7) : `widget.after()` était appelé depuis
  la procédure de fenêtre. `mainloop()` relâche le GIL ; réentrer dans Tcl
  depuis une pile qui appartient à Windows tue Python sans laisser de trace. La
  procédure ne fait plus que lire le HDROP et remplir une file.
- **Crash au 2ᵉ changement de langue** (v2.7c) : un exe onefile qui se relance
  hérite de `_PYI_APPLICATION_HOME_DIR`, si bien que le nouveau processus
  réutilisait le dossier d'extraction de son parent. Le 1er redémarrage passait,
  le 2ᵉ échouait sur « interpréteur Python introuvable ». L'environnement est
  désormais purgé avant la relance.
- **« Info Profil » lisait la ligne affichée, pas la source** (v2.7) : dès le
  premier tri, l'onglet Profils se serait rempli avec les réglages d'une autre
  source, sans rien signaler.
- **Un profil enregistré perdait son filtre de types, en silence** (v3.1) :
  sortir le groupe « Filtres » du formulaire avait retiré sa clé des variables
  du formulaire.
- **Le journal filtrait par entrée, pas par ligne physique** (v3.1) : la sortie
  d'IntellaCmd arrive en un seul appel contenant des dizaines de retours à la
  ligne, si bien que la recherche gardait le bloc entier — cinquante lignes pour
  une seule qui correspond. Cela se présentait comme « la recherche ne marche
  que sur warning » ; les warnings sont mono-ligne.
- **« Voir les réglages de la source… » s'ouvrait vide** (v3.1a) : une constante
  de couleurs était partie avec du code supprimé et deux lignes l'appelaient
  encore — `NameError` juste après l'en-tête, une fenêtre de 940×600 avec deux
  lignes dedans, et aucune erreur nulle part.
- **Le fichier MIME cumulatif était classé par date** (v3.1a) : deux fichiers
  écrits dans la même seconde portent la même date, et le tri retombait alors
  sur leur nom — un import tout juste enregistré pouvait être écrasé par un
  fichier plus ancien.

### Comment ils ont été trouvés, et ce qui les attrape maintenant

Presque aucun n'est visible par la suite de tests : elle ne couvre **aucun
widget**, à dessein. Deux scripts ont été ajoutés :

```powershell
python tests\manuel_construction.py    # construit la fenêtre SANS l'afficher
python tests\manuel_fumee_v3.py <écran>
```

`manuel_construction.py` ne vole jamais le focus : il reste utilisable pendant
que quelqu'un travaille sur le poste, et c'est lui qui a attrapé le filtre de
profil débranché. Et `tests/test_noms_definis.py` est une passe AST qui échoue
dès qu'un module cite un nom que rien ne définit — `py_compile` ne regarde
jamais que la syntaxe.

## Mise à jour depuis la v2.5

Rien à migrer. Les profils (`profils/*.json`), le fichier de réglages
(`intellafeeder.ini`) et le cache par cas (`IF_<cas>.info`) sont relus tels
quels. De nouvelles clés apparaissent au `.ini` au premier lancement
(`density`, `font_scale`, `recursive_default`, `default_profile`, `enable_dnd`).

⚠ Si vous gardez un dossier `lang/` à côté de l'exécutable, ses fichiers restent
**prioritaires** sur les langues embarquées — et des fichiers de v2.5 n'auront
aucune des chaînes ajoutées depuis. Supprimez-les (les langues FR/US intégrées
sont complètes), ou régénérez le dossier depuis Maintenance → Fichiers.
