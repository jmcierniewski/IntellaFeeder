## 1. HAUTE — Injection de commande dans le `.bat` via `<name>` et `<user>` du `case.xml`

**Référence :** `json_builder.py:57-63` et `json_builder.py:70-75`

```python
cmd = f'"{exe}" -u "{user}" -c "{_strip_trailing(case_path)}"'
if case_name.strip():
    cmd += f' -cn "{case_name.strip()}"'
```

**Vecteur (démontré de bout en bout) :**
1. `case_meta.read_case_xml` lit `<name>` et `<user>` du `case.xml` du dossier de cas — fichier XML **sur le partage**, dont le contenu n'est contrôlé ni par l'application ni par l'analyste (`case_meta.py:77` et `case_meta.py:81`).
2. Ces deux valeurs sont poussées **telles quelles** dans des champs en lecture seule de l'interface : `ui.py:361` `self.var_user.set(meta.get("user", ""))` et `ui_import.py:847` `self.var_casename.set(meta["name"])`. L'analyste ne peut donc même pas les corriger.
3. `ui_import.py:1838-1841` les remet dans `params["user"]` / `params["casename"]`, `generator.py:44` puis `generator.py:86` les passe à `import_one_command`.
4. La ligne obtenue est écrite littéralement dans le `.bat` (`json_builder.py:103-105`) — le `cmd` n'est **pas** passé par `_echo_safe`, seul le `label` l'est.
5. `ui_import.py:2121-2122` exécute ce `.bat` : `subprocess.Popen(["cmd", "/c", bat, json_builder.BAT_AUTO_FLAG], …)`.

Un `case.xml` contenant `<name>Dossier 42" &amp; powershell -w hidden -enc &lt;…&gt; &amp; rem </name>` produit dans le `.bat` : `… -cn "Dossier 42" & powershell -w hidden -enc <…> & rem "` → le guillemet ferme la citation, `&` chaîne une commande arbitraire. Le guillemet est interdit dans un **chemin** Windows mais parfaitement légal dans le champ texte `<name>` d'un `case.xml`. Aucun garde en amont : `validation.collect` (`validation.py:15-62`) ne contrôle que la présence/existence des champs, jamais leur contenu.

**Impact :** exécution de code arbitraire sur le poste de l'analyste, avec ses droits et ses sessions SMB ouvertes sur les pièces à conviction, au moment où il clique « Importer ». Le cas piégé peut être un cas reçu d'un tiers, restauré d'une sauvegarde, ou simplement un dossier déposé sur un partage écrivable.

**Correctif proposé :**
- Ne plus construire de chaîne : faire produire par `import_one_command` une **liste d'arguments**, et l'écrire dans le `.bat` via `subprocess.list2cmdline(argv)`, qui applique les règles de citation Win32 (doublement des `"` et des `\` avant guillemet). Le doublement des `^`/`&` restant à la charge de `cmd`, ajouter un échappement `caret` sur `&<>|^` **hors** des paires de guillemets.
- Et, en défense en profondeur, rejeter à la source : dans `generator.generate`, lever si `case_name` ou `user` contient un caractère de `"` `&` `|` `<` `>` `^` `%` `\r` `\n` (message : « nom de cas invalide dans case.xml »). Les noms de cas légitimes n'en contiennent aucun.
- Même traitement pour `extra` (`generator.py:38` → `json_builder.py:61-62` et `73-74`) : ce champ est saisi par l'analyste, donc moins critique, mais il est aussi **persisté dans l'ini** (`ui_import.py:1857`), ce qui rétablit un vecteur si l'ini est écrivable par un tiers.

## 2. MOYENNE — Définitions de tâches d'un cas étranger recopiées verbatim puis rejouées par IntellaCmd

**Référence :** `case_export.py:379-388`, `case_export.py:571`, `task_builder.py:64-68`

```python
# case_export.py:384-388
data = json.loads(raw)
...
return [t for t in data if isinstance(t, dict)] if isinstance(data, list) else []
```

```python
# task_builder.py:64-67
objs = [tasks[i]["obj"] for i in indices]
...
write_json(objs, path)
```

**Vecteur :** le bloc `<tasks>` de chaque `<source>` du XML d'inventaire est désérialisé sans aucune validation de schéma (`_task_objs`), agrégé dans `inventory["case_tasks"]` (`case_export.py:571`), proposé par le menu « Tâches du cas (inventaire) » (`ui_import.py:924-957`), puis réécrit **octet pour octet** dans `task_T1_T2.json` par `task_builder.build_combo_files`, fichier référencé comme `taskFile` dans le JSON de source (`json_builder.py:46-47`) et exécuté par IntellaCmd à l'import. `task_builder.tasks_from_objs` ne vérifie que `isinstance(obj, dict)` (`task_builder.py:34-38`). Le commentaire de `case_export._source_options` (`case_export.py:361-363`) indique que les cas Intella portent des réglages `scriptEnabled` / `scriptType` / `scriptValidated` : le modèle de tâches Intella comporte donc une notion de script.

**Statut :** propagation **démontrée** (aucun filtrage sur tout le chemin) ; la portée exacte de l'impact dépend de la sémantique des tâches Intella (non vérifiable depuis ce dépôt) — **non démontré** qu'une tâche puisse exécuter du code arbitraire.

**Impact :** rejouer sur un cas de travail les tâches d'un cas non maîtrisé revient à importer une configuration active sans revue. Au minimum : altération silencieuse du traitement des pièces (filtres, actions post-indexation) ; au pire, exécution de script côté Intella.

**Correctif proposé :** dans `task_builder.tasks_from_objs`, appliquer une **liste blanche de clés** de premier niveau (`id`, `name`, `conditions`, `actions`, …) et rejeter — ou au moins compter et afficher — toute tâche portant une clé `script*`. Et faire afficher par `_use_case_tasks` le nom **et** le résumé des actions des tâches recyclées, pas seulement leur nombre (`ui_import.py:954-957`).

## 3. MOYENNE — Le `%` n'est pas neutralisé dans les chemins écrits au `.bat` : une source peut être silencieusement non importée

**Référence :** `generator.py:74` et `generator.py:84-85`, consommés par `json_builder.py:60` et `json_builder.py:74`

```python
# generator.py:74
base = f"{safe}_{prefix}{idx:02d}_{config.sanitize_filename(source.name)}"
```

```python
# json_builder.py:60 / 74
cmd += f' -addSourcesFromJson "{sources_json_path}"'
cmd += f' > "{log_path}" 2>&1'
```

**Vecteur :** `config.sanitize_filename` (`config.py:207`) filtre `<>:"/\|?*` et les caractères de contrôle mais **laisse passer `%`**, légal dans un nom de dossier NTFS. Une pièce déposée dans `\\NAS\PV\Scellé %2024%` donne `source.name = "Scellé_%2024%"` (via `path_parser.derive_name`), donc un JSON réellement nommé `…_01_Scellé_%2024%.json`, tandis que la ligne du `.bat` est **développée par cmd.exe** avant exécution : `%2024%` disparaît ou est remplacé. IntellaCmd reçoit un chemin inexistant. Or le module documente lui-même (`case_export.py:68-69`) qu'« IntellaCmd renvoie 0 même en échec » : le test `if errorlevel 1` du `.bat` (`json_builder.py:105`) affiche donc **[OK]**, et la redirection `> "…%2024%.log"` est elle aussi mal ciblée. Le même mécanisme s'applique au dossier du cas (`safe`) et à `log_path`.

**Impact :** une pièce à conviction absente du cas avec un compte rendu au vert — le pire mode de défaillance possible pour cet outil. Accessoirement, la redirection peut écrire à un emplacement non prévu si la variable développée est un chemin.

**Correctif proposé :** ajouter `%` (et `!`, par sécurité si `enabledelayedexpansion` était un jour activé) à la classe filtrée de `config.sanitize_filename` — ou, si le nom doit rester fidèle, doubler les `%` en `%%` au moment d'écrire la ligne dans le `.bat`. Et faire vérifier par le `.bat` l'existence du JSON avant appel : `if not exist "…" (echo [ECHEC] JSON introuvable)`.

## 4. MOYENNE — Le XML d'inventaire reste indéfiniment dans `%TEMP%`

**Référence :** `case_export.py:112-113` et `case_export.py:150`

```python
tmpdir = tempfile.mkdtemp(prefix="intellafeeder_export_")
xml_path = os.path.join(tmpdir, "sources.xml")
...
inventory["xml_path"] = xml_path
```

**Vecteur :** `sources.xml` contient la liste complète des chemins de pièces, noms de scellés, tailles et définitions de tâches du cas. Aucun `shutil.rmtree` n'existe dans le projet (recherche `rmtree` : uniquement `tests/manuel_fumee_dnd_reel.py:143`), et le chemin est délibérément conservé pour réutilisation (`ui_export.py:961-982`). Chaque lecture de cas — et **chaque sous-cas** d'un compound, cf. `case_export.py:203` — laisse donc un dossier de plus.

**Impact :** accumulation permanente de métadonnées de procédures dans le profil utilisateur, hors du périmètre du cas : reprise par les sauvegardes, les profils itinérants et les outils de synchronisation ; récupérable après clôture du dossier. Pas de fuite inter-utilisateurs (`%TEMP%` est par profil sous Windows), d'où MOYENNE et non HAUTE.

**Correctif proposé :** enregistrer les `tmpdir` créés dans une liste de module et les supprimer (`shutil.rmtree(..., ignore_errors=True)`) à la fermeture de l'application ou dès qu'un nouvel inventaire remplace le précédent ; à défaut, purger au démarrage tous les `intellafeeder_export_*` de `tempfile.gettempdir()` de plus de N heures.

## 5. MOYENNE — `-log DEBUG` imposé et flux IntellaCmd recopiés intégralement dans le journal applicatif

**Référence :** `case_export.py:115-116` et `case_export.py:128-131`

```python
cmd = [exe, "-u", user, "-c", case_loc, "-exportSourceList", xml_path,
       "-log", "DEBUG"]
...
if proc.stdout:
    log("stdout IntellaCmd :\n" + proc.stdout.strip())
```

**Vecteur :** le niveau `DEBUG` est câblé en dur, sans option, et l'intégralité de `stdout`/`stderr` part dans `AppLog` (`app_log.py:17-21`), qui conserve tout en mémoire, l'affiche dans l'onglet Journal et l'écrit sur disque à la demande (`app_log.export`, `app_log.py:31-33`). Les traces DEBUG d'un moteur d'indexation contiennent chemins de pièces, noms de fichiers et messages d'erreur par ressource. Même chemin pour `report["error"] = str(exc)` (`case_export.py:259`), remonté ensuite à l'écran par sous-cas.

**Impact :** un export de journal destiné au support technique ou joint à un ticket emporte des métadonnées de procédure. Le sujet est explicitement cadré par les règles du poste (« la forme, pas le fond »).

**Correctif proposé :** passer à `-log INFO` par défaut et n'activer `DEBUG` que via un paramètre explicite de `run_export_source_list` (déclenché par une case « diagnostic » de l'interface) ; ne journaliser par défaut que les N premières lignes de `stderr` et un compteur d'octets pour `stdout`. Conserver `diagnose_no_xml` (`case_export.py:66-94`), qui donne déjà le diagnostic utile **sans** recopier les flux.

## 6. MOYENNE — Injection de formule dans le CSV d'inventaire

**Référence :** `case_export.py:589-595`

```python
with open(path, "w", newline="", encoding="utf-8-sig") as f:
    writer = csv.DictWriter(f, fieldnames=columns, extrasaction="ignore")
```

**Vecteur :** les valeurs des colonnes « Nom », « Chemin » et « Tâches » proviennent du XML d'inventaire (`case_export.py:512-522`), donc des noms de sources et de dossiers du cas, et sont écrites sans préfixe de neutralisation. L'encodage `utf-8-sig` est là, de l'aveu du docstring, « pour Excel ». Un scellé ou un dossier de pièces nommé `=cmd|'/C calc'!A1` (nom de dossier légal sur un partage Samba) devient une cellule active à l'ouverture.

**Impact :** exécution de code à l'ouverture du CSV par l'analyste ou par un destinataire du rapport — Excel affiche des avertissements pour DDE mais l'attaque reste opérante via les formules d'exfiltration (`=WEBSERVICE(...)`, liens hypertexte), d'où MOYENNE.

**Correctif proposé :** dans `export_csv`, préfixer d'une apostrophe toute valeur dont le premier caractère est `=`, `+`, `-`, `@`, `\t` ou `\r` avant l'écriture — une fonction `_csv_safe(v)` de trois lignes appliquée dans la compréhension de `writer.writerow`.

## 7. MOYENNE — Le `.bat` exécuté est écrit à côté de l'exécutable, dans un dossier aux ACL non maîtrisées

**Référence :** `generator.py:50-57`

```python
scripts_dir = config.case_scripts_dir(case_name)
...
os.makedirs(scripts_dir, exist_ok=True)
```

**Vecteur :** `config.case_scripts_dir` → `config.case_dir` → `config.base_dir()` = **dossier de l'exécutable** (`config.py:142-146`, `config.py:212-218`). Si l'outil est déployé sur un partage d'équipe ou dans un dossier utilisateur écrivable par des tiers — déploiement plausible pour un `.exe` PyInstaller diffusé en interne — alors `Cas\<cas>\scripts\<cas>_import.bat` est modifiable par un tiers entre la génération et le lancement. `ui_import._main_bat_path` (`ui_import.py:2061-2067`) retrouve ce fichier **par son nom**, sans contrôle d'intégrité, et `ui_import.py:2121` l'exécute.

**Statut :** exploitabilité **conditionnée au déploiement** (non vérifiable depuis le code) ; la fenêtre TOCTOU, elle, est structurelle.

**Impact :** exécution de code dans le contexte de l'analyste, au moment exact où il a ses sessions SMB ouvertes sur les pièces.

**Correctif proposé :** écrire les scripts sous `%LOCALAPPDATA%\IntellaFeeder\Cas\…` (ou un dossier choisi et vérifié) plutôt que sous `base_dir()` ; et, à défaut, faire calculer par `generate` un SHA-256 du `.bat` retourné dans `report`, que `importer()` revérifie avant le `Popen`.

## 8. BASSE — `_strip_trailing` détruit une racine de lecteur (`X:\` → `X:`)

**Référence :** `json_builder.py:16-18`, même défaut à `generator.py:43`

```python
def _strip_trailing(path: str) -> str:
    return path.rstrip().rstrip("\\/")
```

**Vecteur :** `path_parser.normalize_path` protège explicitement la racine (`path_parser.py:15-16` : « ne pas réduire "C:\\" à "C:" »), mais ces deux emplacements réimplémentent le nettoyage sans cette protection. Un cas placé à la racine d'un lecteur réseau mappé (`X:\`) devient l'argument `-c "X:"`, qui désigne pour un processus Windows **le répertoire courant du lecteur X**, pas sa racine.

**Impact :** IntellaCmd cible un dossier de cas autre que celui affiché à l'écran. Faible probabilité (un cas est rarement à la racine), effet silencieux.

**Correctif proposé :** remplacer les deux occurrences par `path_parser.normalize_path(...)`, déjà chargé de ce contrat.

## 9. BASSE — `build_single_source_json` accepte n'importe quelle clé d'option (aujourd'hui couvert en amont)

**Référence :** `json_builder.py:42-47`

```python
_BASE = ("name", "evidencePath", "sourceType", "timezone")
for k, v in (options or {}).items():
    if k not in _BASE:
        obj[k] = v
```

**Vecteur : couvert.** La liste noire `_BASE` ne protège que 4 clés — pas `taskFile`, écrite juste après, ni aucune future clé sensible. Les options viennent toutefois de `profiles.emit_map` → `profile_catalog.diff_from_default`, qui **itère sur le catalogue** `OPTIONS` (`profile_catalog.py:155-162`) : aucune clé étrangère ne peut passer, y compris via un profil créé depuis les `index_options`/`source_options` d'un `case.xml` importé. Signalé comme contrat fragile, non comme faille : le jour où un appelant fournira des options non filtrées, l'injection de clés dans le JSON d'import redevient possible.

**Correctif proposé :** transformer `_BASE` en liste **blanche** appuyée sur `profile_catalog.OPTIONS` : `if k in profile_catalog.OPTIONS and k not in _BASE`, et journaliser les clés écartées.

## 10. BASSE — `ET.parse` sans durcissement (expansion d'entités)

**Référence :** `case_export.py:446`

```python
tree = ET.parse(xml_path)
```

**Vecteur : non démontré.** Le fichier parsé est toujours celui qu'IntellaCmd vient d'écrire dans un `mkdtemp` au nom imprévisible (`case_export.py:112-138`) : aucun chemin de code du dépôt ne fait passer à `parse_source_list_xml` un XML choisi par l'utilisateur (seul `tests/test_profile_settings_view.py:37` le fait). `xml.etree.ElementTree` ne résout pas les entités externes (pas de XXE, pas de récupération de DTD), mais reste sensible à l'expansion d'entités internes (« billion laughs ») → déni de service mémoire. La fonction étant publique et déjà appelée sur des XML arbitraires en test, la surface existe si un jour l'interface propose « ouvrir un `sources.xml` existant ».

**Correctif proposé :** parser avec `ET.XMLParser()` dont on désactive la DTD, ou refuser en tête de fonction tout fichier dont les 4 premiers Ko contiennent `<!DOCTYPE` ou `<!ENTITY`. Coût nul, garde définitive.

## Remarques mineures

- `case_export.py:589-591` — `export_csv` écrase sans confirmation et sans écriture atomique ; une interruption laisse un CSV tronqué qui ressemble à un inventaire complet.
- `case_export.py:60-63` — `_split_args` retombe silencieusement sur `extra.split()` quand `shlex` échoue (guillemet non fermé) : les arguments changent de sens sans avertir.
- `case_export.py:61` — `shlex.split(posix=False)` conserve les guillemets **dans** le jeton ; `subprocess` les re-cite ensuite, donc un argument à valeur entre guillemets arrive déformé à IntellaCmd.
- `json_builder.py:83-87` — `_echo_safe` ne neutralise pas `!` ; sans effet aujourd'hui, le `.bat` faisant `setlocal` sans `enabledelayedexpansion` (`json_builder.py:101`) — à retenir si l'expansion différée était activée.
- Aucun des fichiers produits (JSON de sources, fichiers de tâches, `.bat`, journaux) ne reçoit d'ACL restrictive ; ils héritent du dossier parent et contiennent les chemins des pièces.
- `generator.py:48` — `float(params["limit_gb"])` sans garde ; l'appelant normalise (`ui_import.py:1828-1832`), donc sans conséquence hors appel programmatique.
- Noms réservés Windows (`NUL`, `CON`, `COM1`…) : **non exploitables** ici, les fichiers produits étant toujours préfixés (`{safe}_{NN}_`, `task_T1…`) ; seul un cas littéralement nommé `NUL` ferait échouer `os.makedirs` (`generator.py:56`), soit un refus propre.

## Ce qui est correct

- L'inventaire lance IntellaCmd **sans shell et par liste d'arguments** (`case_export.py:115-124`), avec `timeout` et `errors="replace"` : ni le nom d'un sous-cas ni un chemin déclaré dans un `case.xml` compound ne peuvent y injecter de commande — c'est la moitié saine du projet, et c'est exactement le modèle à reporter sur `json_builder`.
- La traversée de chemin par le nom de cas ou de source est effectivement bloquée : `config.sanitize_filename` (`config.py:204-209`) neutralise séparateurs, deux-points et caractères de contrôle, et `strip("._ ")` élimine `..` — un nom `..\..\Windows` retombe sur un segment inoffensif.
- Les JSON sont produits par `json.dump(..., ensure_ascii=True)` (`json_builder.py:50`, `task_builder.py:18`) : aucune injection de contenu possible dans le JSON généré, quel que soit le nom de la pièce.
- Aucun secret en dur, aucun identifiant de partage, aucun `eval`/`exec`/`pickle`/`yaml.load`/import dynamique, aucun accès réseau direct dans les quatre fichiers ; `mkdtemp` (nom imprévisible, fichier non pré-créé) est le bon choix pour le XML temporaire.
