## Propositions de tests, par risque décroissant

### 1. Segments non retrouvés quand la casse du chemin diffère de celle du disque

**Catégorie** : Boundary / Logic — **Risque** : High — **Réf.** : `sizing.py:105-106`

**Entrée** : `img.E01` (100 o) et `img.E02` (200 o) sur disque ; appel
`sizing.image_size(".../IMG.E01")` — casse différente de celle du disque.

**Attendu** : 300, comme `test_ewf_somme_tous_les_segments` qui emploie la même casse
partout.

**Pourquoi ça peut échouer** : `_image_segments` compare
`os.path.splitext(n)[0] == stem` **sans normaliser la casse**, alors que l'extension est
explicitement abaissée juste à côté (`os.path.splitext(n)[1].lower()`). L'asymétrie du
code trahit un oubli plutôt qu'un choix. Sur un système de fichiers Windows (insensible à
la casse), `os.path.exists("IMG.E01")` renvoie vrai malgré tout : la fonction entre dans
`_image_segments`, le stem `IMG` ne correspond à aucune entrée réelle en minuscules,
`segments` est vide, on retombe sur `[path]`, et `_safe_size` réussit — en ne comptant
que le premier segment.

C'est exactement la sous-évaluation de volume corrigée le 18/09/2026, par un autre
déclencheur : un chemin collé ou tapé dans une casse différente de celle du disque.

**Fichier** : `tests\test_sizing.py`, `TestImageSize`, cas paramétré sur la casse.

### 2. `cache_key` ignore l'alias d'hôte NetBIOS / IP d'un même partage

**Catégorie** : Logic — **Risque** : High — **Réf.** : `sizing.py:153-155`

**Entrée** : `measure_sources` pour une source `\\NAS\part\Source`, avec un cache portant
la clé de `\\10.0.0.1\part\Source`.

**Attendu** : le comportement déjà retenu ailleurs dans le projet
(`path_parser.share_key`, incident du 08/09/2026) — un même partage désigné par nom
NetBIOS ou par IP doit être reconnu comme identique.

**Pourquoi ça peut échouer** : `cache_key` fait `normalize_path(path).lower()`, pas
`share_key`, qui existe précisément pour neutraliser l'hôte UNC et que
`case_export.build_inventory` emploie déjà pour ce même problème. Une source déjà mesurée
et mise en cache sous un nom d'hôte n'est pas retrouvée si elle se présente ensuite par
son IP : le cache rate en silence, et un dossier de NAS potentiellement énorme est
re-scanné en entier.

⚠ **Voir la Vérification n° 3** : le diagnostic est incomplet, la correction ne peut pas
se faire dans `sizing` seul.

**Fichier** : `tests\test_sizing.py`, nouvelle classe `TestCacheKeyAliasHote`.

### 3. `os.walk` avale une erreur réseau survenue en cours de scan

**Catégorie** : Error Handling — **Risque** : High — **Réf.** : `sizing.py:72`

**Entrée** : arborescence dont un sous-dossier devient illisible à mi-parcours
(monkeypatch d'`os.walk` / `os.scandir` simulant une déconnexion SMB), sans que
`should_stop` ne soit jamais vrai.

**Attendu**, d'après le contrat en tête de module : une mesure interrompue en cours ne
doit **jamais** être enregistrée comme complète.

**Pourquoi ça peut échouer** : `folder_size` itère sur `os.walk(path)` sans callback
`onerror`. Par défaut, `os.walk` avale silencieusement toute erreur de listage et
poursuit. Une perte de connexion SMB à mi-scan — le contexte métier dit le partage
« parfois injoignable » — ne déclenche ni exception ni `should_stop` : `folder_size`
renvoie un total tronqué, `measure_sources` le tient pour complet (`cancelled` reste
faux), il est posté en `"row"`, mis en cache et persisté.

Le contrat d'annulation ne couvre que l'arrêt coopératif ; les erreurs d'E/S passent
dessous.

**Fichier** : `tests\test_sizing.py`, nouvelle classe `TestErreursIO`.

### 4. Un fichier verrouillé est compté comme 0 octet

**Catégorie** : Error Handling — **Risque** : Medium-High — **Réf.** : `sizing.py:55-59`

**Entrée** : dossier de 2 fichiers, dont un pour lequel `os.path.getsize` lève `OSError`
(fichier verrouillé par un antivirus, PST ouvert dans Outlook).

**Attendu** : au minimum une trace disant que le total est incomplet.

**Pourquoi ça peut échouer** : `_safe_size` intercepte `OSError` et renvoie 0, sans trace
ni indicateur. Un gros fichier verrouillé est silencieusement compté comme vide. Même
risque de sous-évaluation que le cas précédent, au niveau du fichier.

**Fichier** : `tests\test_sizing.py`, `TestErreursIO`.

### 5. `read_tasks2` tronque la liste dès la première entrée malformée

**Catégorie** : Error Handling / Logic — **Risque** : Medium — **Réf.** : `case_meta.py:125-140`

**Entrée** : `prefs\tasks2.json` = `[{"name": "TacheOK"}, "pas_un_dict", {"name": "TacheApres"}]`.

**Attendu** : ignorer l'entrée invalide et poursuivre, ou documenter que la liste peut
être partielle.

**Pourquoi ça peut échouer** : `json.load` **et** la boucle d'extraction sont dans le même
`try`. L'`except (ValueError, OSError, AttributeError)` intercepte aussi l'`AttributeError`
levée par `t.get(...)` quand un élément n'est pas un dict — et cet `except` **coupe la
boucle**. `TacheOK` est conservée, `TacheApres` est perdue, sans signal. Le nombre de
tâches affiché peut être inférieur à la réalité selon la position de l'entrée corrompue.

**Fichier** : `tests\test_case_meta_compound.py` ou un nouveau `tests\test_case_meta.py`.

### 6. `image_size` interrompu au milieu des segments

**Catégorie** : Boundary — **Risque** : Medium — **Réf.** : `sizing.py:110-128`

**Entrée** : image à 3 segments, `should_stop` devenant vrai après le premier segment
mesuré — le pendant de `test_folder_size_stoppe_et_rend_le_partiel`.

**Attendu** : total partiel rendu, et rejet par `measure_sources`.

**Pourquoi ça peut échouer** : rien ne le laisse penser, le code est structurellement
identique à `folder_size`. Mais ce chemin n'est testé nulle part :
`test_image_size_stoppe` n'emploie que `should_stop=lambda: True`, soit un arrêt avant
même le premier segment. Trou dans la garantie d'annulation, spécifiquement pour les
images multi-segments.

**Fichier** : `tests\test_sizing.py`, `TestAnnulation`.

### 7. `read_subcases(folder)` sur un dossier sans aucun `case.xml`

**Catégorie** : Error Handling — **Risque** : Low-Medium — **Réf.** : `case_meta.py:159-163`

**Entrée** : appel direct, sans `paths`, sur un dossier dépourvu de `case.xml`.

**Attendu** : `[]`, sans lever — contrat explicite de la docstring.

**Pourquoi ça peut échouer** : à la lecture, le chemin paraît correct (`FileNotFoundError`
dérive d'`OSError`, qui est intercepté). Mais aucun test ne l'exerce : tous passent soit
par `read_case`, qui valide `has_case_xml` en amont, soit fournissent `paths`. Il manque
le verrou de non-régression sur une garantie mise en avant par le module.

**Fichier** : `tests\test_case_meta_compound.py`, `TestReadSubcases`.

### 8. `<size>` non entier dans `case.xml` retombe à 0

**Catégorie** : Boundary — **Risque** : Low — **Réf.** : `case_meta.py:69-73`

**Entrée** : `<size>1024.5</size>` ou `<size>1 024</size>`.

**Attendu** : une erreur explicite, ou la documentation du repli à 0.

**Pourquoi ça peut échouer** : `gi()` intercepte `(ValueError, TypeError)` et renvoie 0
sans signal. Cohérent avec « ne lever que si `case.xml` est absent », mais un `<size>`
malformé — qu'Intella écrit et que ce module ne contrôle pas — devient une taille de cas
nulle, ce qui est trompeur pour un garde-fou de volumétrie.

**Fichier** : `tests\test_case_meta_compound.py`, `TestDetection`.

## Vérification des défauts suspectés

Le rapport de l'agent a été contrôlé point par point avant d'être retenu.

### 1. Casse du stem — ✅ **CONFIRMÉ par l'exécution**

Image `img.E01` + `img.E02` + `img.E03` = 350 octets :

| Appel | Résultat | Attendu |
|---|---|---|
| `image_size("img.E01")` | 350 | 350 |
| `image_size("IMG.E01")` | **100** | 350 |
| `image_size("img.e01")` | 350 | 350 |

L'extension supporte le changement de casse, le radical non. Défaut réel, avec l'impact
métier du garde-fou 950 Go.

### 2. `read_tasks2` — ✅ **CONFIRMÉ par lecture**

Le `try` englobe bien la boucle ; une entrée non-dict lève `AttributeError` sur `t.get`,
l'`except` reprend la main hors de la boucle et `return names` rend une liste tronquée.
Portée réelle faible : `tasks2.json` est écrit par Intella, une entrée non-dict y est
improbable. Défaut de robustesse, pas de défaut constaté.

### 3. `cache_key` — ⚠ **CONFIRMÉ, MAIS MAL DIAGNOSTIQUÉ**

Le constat est juste : le cache rate sur un alias d'hôte. Mais la correction proposée
(passer `sizing.cache_key` à `share_key`) **casserait le cache existant**.
`case_info.py:82` emploie exactement la même normalisation —
`path_parser.normalize_path(p).lower()` — pour les clés **persistées dans `IF_<cas>.info`**.
Les deux modules sont donc cohérents entre eux ; changer l'un sans l'autre rendrait
illisibles toutes les mesures déjà enregistrées.

Si ce point est repris, il se traite dans `sizing` **et** `case_info` ensemble, avec une
stratégie de reprise des clés déjà écrites. Ce n'est plus un correctif, c'est une
migration.

### 4. `os.walk` sans `onerror` — ✅ **FACTUEL**, portée à trancher

`os.walk` ignore effectivement les erreurs de listage par défaut. Reste à décider s'il
s'agit d'un défaut ou d'un choix : `forensic_scan.scan_folder` documente explicitement le
même comportement comme voulu (« les dossiers illisibles sont ignorés en silence »).
`sizing`, lui, ne le dit pas — et son enjeu métier n'est pas le même : ignorer un dossier
lors d'une collecte de chemins fait manquer une source, visible ; l'ignorer lors d'une
mesure fausse un volume, invisible.

## Ce qui n'est pas retenu

`declared_path` (`case_meta.py:171-186`) stocke le chemin résolu et normalisé pour une
entrée relative, là où la docstring du module promet « le chemin tel qu'écrit dans le
`case.xml` ». Léger décalage de documentation, cohérent avec l'usage réel (repli
fonctionnel). Pas un défaut ; mériterait un test qui fixe le choix.
