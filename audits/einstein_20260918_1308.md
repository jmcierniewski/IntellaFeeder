### 1. [SÉVÉRITÉ HAUTE] Détection des segments d'image dupliquée et divergente sur 3 modules — sous-comptage de volume possible

- **Référence** : `sizing.py:27-29` (voir aussi `forensic_scan.py:36-45` et `path_parser.py:9-12`)

```python
_RE_EWF = re.compile(r"\.e\d{2}$", re.IGNORECASE)   # .E01, .E02, ...
_RE_SPLIT_DD = re.compile(r"\.\d{3}$")              # .001, .002, ...
_RE_AD1 = re.compile(r"\.ad\d+$", re.IGNORECASE)    # .ad1, .ad2, ... .ad28
```

- **Classification** : Accidental Complexity (duplication de connaissance métier, incohérente entre copies).
- **Constat** : trois fichiers réimplémentent chacun leur propre liste de familles d'extensions d'images forensiques :
  - `path_parser._RE_EWF/_RE_DD/_RE_SPLIT/_RE_AD1` (avertissement « segment non initial »),
  - `sizing._RE_EWF/_RE_SPLIT_DD/_RE_AD1` (**calcul du volume total**, `_image_segments`),
  - `forensic_scan._FAMILIES` (8 familles : EWF, EWF>.E99, EWFv2 `.ex01`, LEF `.l01`, LEF `.lx01`, SMART `.s01`, AD1, brut `.001`).

  `sizing.py` est la copie la plus **incomplète** : elle ne reconnaît ni `.ex01` (EWFv2), ni `.l01`/`.lx01` (LEF), ni `.s01` (SMART) — alors que `forensic_scan.py` les accepte comme images forensiques valides dans le panneau d'import. Pour ces formats, `_image_segments()` ne matche aucun pattern, retombe sur `[path]` et `image_size()` **ne somme que le premier segment** au lieu de la totalité de l'image.
- **Simplification concrète** : extraire une table unique des familles de segments (celle, la plus complète, de `forensic_scan._FAMILIES`) dans un module partagé (par ex. `image_families.py`), et faire consommer cette table par `path_parser.is_non_first_segment`, `sizing._image_segments` et `forensic_scan.image_kind/refusal_reason`.
- **Risque de régression** : faible techniquement (la table cible existe déjà et est testée en pratique par le panneau Import) ; le risque réel est plutôt de **ne pas corriger** — le comportement actuel sous-évalue silencieusement la taille d'un cas contenant une image LEF/SMART/EWFv2 multi-segments, ce qui peut faire passer un cas au-delà du garde-fou des 950 Go documenté dans `case_export.py`.

### 2. [SÉVÉRITÉ MOYENNE-HAUTE] Deux référentiels de libellés de type de source, déjà divergents

- **Référence** : `case_export.py:55-58` vs `config.py:24-27`

```python
# case_export.py
_TYPE_LABEL = {
    config.SOURCE_TYPE_DISK_IMAGE: "Image",
    config.SOURCE_TYPE_FOLDER: "Dossier/Fichier",
}
```

```python
# config.py
TYPE_LABELS = {
    SOURCE_TYPE_DISK_IMAGE: "Image",
    SOURCE_TYPE_FOLDER: "Dossier",
}
```

- **Classification** : Accidental Complexity (OR explicite — deux sources de vérité pour la même donnée).
- **Constat** : `config.type_label()` existe déjà comme point d'entrée traduit (et importe `i18n` tardivement pour cette raison), mais `case_export.py` maintient sa propre table, avec un libellé différent pour `SOURCE_TYPE_FOLDER` (« Dossier/Fichier » contre « Dossier »). Le jour où l'un des deux est corrigé (ex. traduction, libellé), l'autre reste silencieusement désynchronisé — c'est déjà arrivé.
- **Simplification concrète** : supprimer `_TYPE_LABEL` dans `case_export.py` et appeler `config.type_label(s["type"])` dans `to_display_rows`. Si le libellé « Dossier/Fichier » est le comportement voulu pour ce tableau précis, le renommer explicitement (ex. `config.TYPE_LABELS_INVENTORY`) pour que la divergence soit assumée et documentée, pas accidentelle.
- **Risque de régression** : très faible — changement de libellé affiché uniquement, à vérifier dans la colonne « Type » du tableau d'inventaire.

### 4. [SÉVÉRITÉ MOYENNE] `run_export_subcases` réimplémente manuellement une fusion d'inventaires

- **Référence** : `case_export.py:181-192`

```python
rows: list = []
reports: list = []
xml_paths: list = []
existing_paths: set = set()
existing_share_keys: set = set()
```

- **Classification** : Accidental Complexity.
- **Constat** : la fonction déclare 9 accumulateurs locaux (`rows`, `reports`, `xml_paths`, `existing_paths`, `existing_share_keys`, `folder_unknown`, `sources_detail`, `case_tasks`, `seen_task_sigs`, `known_bytes`, `ok_count`) puis, pour chaque sous-cas, va piocher à la main dans le dict retourné par `build_inventory()` (via `run_export_source_list`) pour les recombiner un par un (l. 243-266) avant de les remballer dans un dict de même forme (l. 274-291). C'est une fusion de N inventaires en 1, faite « à la main » plutôt que par une fonction générique réutilisable — la logique de dédoublonnage des tâches (l. 257-261) duplique d'ailleurs textuellement celle de `build_inventory` (l. 533-538).
- **Simplification concrète** : extraire un `merge_inventories(sub_invs: list[dict]) -> dict` réutilisant le même schéma de dédoublonnage de tâches (`_task_signature`) qu'utilise déjà `build_inventory`, appelé une fois en fin de boucle plutôt que fusionné champ par champ pendant la boucle.
- **Risque de régression** : moyen — fonction longue et sensible (gestion d'échecs partiels par sous-cas) ; à couvrir par les tests déjà existants sur le cas compound avant refactor (le fichier mentionne explicitement des tests de non-régression sur ce sujet).

### 5. [SÉVÉRITÉ MOYENNE] État module global mutable non encapsulé dans `mime_catalog.py`

- **Référence** : `mime_catalog.py:72-80`

```python
_descriptions: dict[str, str] = {}
_observed: set[str] = set()
_user: dict[str, str] = {}      # descriptions saisies par l'utilisateur
```

- **Classification** : Accidental Complexity (sur-ingénierie inversée : un module procédural avec état caché là où un petit objet suffirait).
- **Constat** : 6 variables globales (`_descriptions`, `_observed`, `_user`, `_source_file`, `_external`, `_duplicates`) sont modifiées par `load()` et lues par une douzaine de fonctions (`label`, `status`, `origin`, `stats`, `search`…). Le module entier repose sur une précondition implicite (« `load()` a été appelé ») non vérifiable par les appelants autrement qu'en observant `is_loaded()`. C'est un couplage temporel caché — l'ordre d'appel compte, mais rien dans les signatures ne le montre.
- **Simplification concrète** : regrouper cet état dans une petite classe (`MimeCatalog`) instanciée une fois (ou un singleton explicite), avec `load()` comme constructeur/méthode et les fonctions actuelles en méthodes. Le comportement observable ne change pas.
- **Risque de régression** : moyen — module central (référentiel MIME), utilisé par `profile_translate.py` et par l'UI ; à ne toucher qu'avec une suite de tests de non-régression sur `load()`/`import_descriptions()`/`learn()`.

### 6. [SÉVÉRITÉ BASSE-MOYENNE] Double parcours de `_FAMILIES` pour une seule classification

- **Référence** : `forensic_scan.py:76-81`

```python
def refusal_reason(path: str) -> str:
    name = os.path.basename(path)
    ext = os.path.splitext(name)[1].lower()
    if image_kind(path):
        return ""
```

- **Classification** : Accidental Complexity.
- **Constat** : `refusal_reason()` commence par rappeler `image_kind(path)` (qui boucle déjà sur `_FAMILIES`), puis, si ce n'est pas un segment initial, reboucle une seconde fois sur `_FAMILIES` (l. 84-86) pour distinguer « segment non initial » d'« extension inconnue ». Deux passes pour classer une seule extension.
- **Simplification concrète** : une fonction unique `_classify_ext(ext) -> tuple[str, str]` (kind, reason) parcourant `_FAMILIES` une fois, dont `image_kind()` et `refusal_reason()` deviennent de simples projections.
- **Risque de régression** : très faible — logique pure, aucune E/S, facilement vérifiable par les mêmes cas de test existants (extensions EWF/AD1/SMART/etc.).

### 7. [SÉVÉRITÉ BASSE] Import tardif d'`i18n` dupliqué dans `config.py` pour casser un cycle

- **Référence** : `config.py:30-32` (voir aussi lignes 147-148)

```python
def type_label(source_type: str) -> str:
    """Libellé traduit d'un type de source (import tardif, cf. ``human_size``)."""
    import i18n
```

- **Classification** : Accidental Complexity (contournement structurel dupliqué plutôt que corrigé une fois).
- **Constat** : `type_label()` et `human_size()` font chacune un `import i18n` local pour éviter un cycle `config` / `i18n`. Le commentaire renvoie explicitement l'une à l'autre — le contournement est donc assumé, mais dupliqué.
- **Simplification concrète** : si le cycle est structurel (i18n a besoin de constantes de config, config a besoin de traductions), extraire les deux fonctions dépendantes de `i18n` (`type_label`, `human_size`) dans un petit module `formatting.py` qui importe librement `config` et `i18n` sans cycle — un seul point d'import tardif au lieu de deux.
- **Risque de régression** : faible, mais touche potentiellement de nombreux appelants (`config.human_size` est utilisé largement, y compris dans `case_export.py`) — à faire par déplacement pur (pas de changement de signature) et grep exhaustif des appelants avant renommage de module.

### 8. [SÉVÉRITÉ BASSE] Repli silencieux `shlex.split` vers `str.split()` sur erreur de guillemets

- **Référence** : `case_export.py:66-69`

```python
    try:
        return shlex.split(extra, posix=False)
    except ValueError:
        return extra.split()
```

- **Classification** : Accidental Complexity (deuxième chemin de code pour le même besoin, changeant silencieusement la sémantique de découpage).
- **Constat** : en cas de guillemet non fermé dans les arguments supplémentaires IntellaCmd, la fonction bascule sur un découpage naïf par espaces qui casse la valeur des arguments contenant des espaces entre guillemets — sans avertir l'appelant (`log` n'est pas accessible ici).
- **Simplification concrète** : remonter l'erreur (ou au moins la signaler via une valeur de retour distincte / lever une exception explicite avec message utilisateur), plutôt que produire un découpage différent et incorrect en silence.
- **Risque de régression** : faible — situation déjà en échec (guillemets mal formés) ; le seul changement observable est un message d'erreur au lieu d'un comportement dégradé silencieux.

### 9. [SÉVÉRITÉ BASSE] Dépendance bidirectionnelle codée en dur pour une seule paire de clés

- **Référence** : `profile_catalog.py:166-169`

```python
    if "sourceTypeFilter" in emit and "sourceTypeFilterMode" not in emit:
        mode = coerce("sourceTypeFilterMode",
                      values.get("sourceTypeFilterMode", OPTIONS["sourceTypeFilterMode"]["default"]))
        emit["sourceTypeFilterMode"] = mode or "exclude"
```

- **Classification** : Essential Complexity (règle métier réelle d'IntellaCmd), mais implémentation en Accidental Complexity légère — deux blocs `if` symétriques câblés en dur plutôt qu'une règle déclarative.
- **Constat** : la dépendance « filtre / mode » entre `sourceTypeFilter` et `sourceTypeFilterMode` est correcte et bien commentée (bug réel du 09/09/2026 documenté), mais n'est pas généralisable si une autre paire dépendante apparaît (ex. `sourceHashFilters`).
- **Simplification concrète** : si une seule paire est à prévoir, laisser tel quel (ne pas sur-généraliser pour un seul cas — ce serait de la sur-ingénierie inverse). Si une deuxième dépendance apparaît, introduire alors une liste `DEPENDENT_PAIRS = [("sourceTypeFilter", "sourceTypeFilterMode", "exclude")]` traitée par une boucle unique.
- **Risque de régression** : nul dans l'immédiat (pas de changement proposé maintenant) — finding informatif, à surveiller.

## Complexity Score global : **Moyen**

Le dépôt est dense (`mime_catalog.py` 621 lignes, `case_export.py` 562 lignes) mais la majorité de cette taille est de la **complexité essentielle** bien documentée : chaque branche inhabituelle renvoie à un incident réel daté (verrou SMB, alias MIME, dédoublonnage de tâches, pause du .bat…), ce qui est le signe d'un code qui a appris du terrain plutôt que d'un code simplement mal structuré. La complexité *accidentelle* identifiée est concentrée sur un nombre restreint de points, dont un seul à impact fonctionnel réel (finding n°1 — sous-comptage de volume sur certains formats d'image), les autres relevant de duplication de tables ou d'état procédural qui alourdissent la maintenance sans compromettre le comportement actuel.

## Trade-offs

- **Corriger le finding n°1** (unifier les familles de segments) : gain direct en fiabilité du garde-fou 950 Go ; coût = toucher trois modules et retester les scénarios d'images multi-segments (EWF, AD1, brut, LEF, SMART).
- **Corriger les findings n°2/3/6** (dédupliquer tables et passes) : gain en maintenabilité future (un seul endroit à modifier quand Intella change), sans changement de comportement observable ; coût de test faible, refactors mécaniques.
- **Corriger le finding n°5** (encapsuler l'état de `mime_catalog`) : gain en testabilité et en clarté d'API ; coût plus élevé car le module est central et largement consommé — à traiter séparément des autres, avec une suite de tests de caractérisation avant refactor.
- **Ne pas toucher** aux findings n°7/8/9 dans l'immédiat sauf besoin concret : leur coût de correction dépasse le bénéfice tant qu'ils ne causent pas d'incident constaté, conformément au principe « aussi simple que possible, pas plus ».
